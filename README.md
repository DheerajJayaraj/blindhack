# MedTwin Pro

**A personal health-record workspace with AI-assisted analysis.**

MedTwin Pro is a full-stack healthcare application designed to bring recorded health measurements, medical conditions, treatments, treatment outcomes, and AI-assisted health-record exploration into one workspace.

The project combines a React dashboard with a FastAPI backend, persistent SQL database storage, and an external AI service for prompt-based analysis. It is designed to make health information easier to organize, review, and explore while keeping the distinction between recorded data and AI-generated explanations clear.

> **Medical disclaimer:** MedTwin Pro is an experimental software project, not a medical device. AI-generated responses may be inaccurate and must not be treated as a diagnosis, prescription, or substitute for qualified medical care.

## Highlights

### Health dashboard
- Overview of recorded measurements, medical conditions, and treatments.
- Latest-measurement summaries and historical measurement trends.
- Dedicated sections for navigating health records.
- Clear empty states when no records are available.

### Health measurements
- Create, retrieve, and list measurement records.
- Store a measurement's name, value, unit, timestamp, optional linked condition, source, and notes.
- Filter measurements by medical condition.
- Visualize recorded readings without automatically inventing targets or predictions.

### Medical conditions
- Create and retrieve condition records.
- Update condition details and status.
- Track conditions using supported statuses: `active`, `resolved`, and `inactive`.

### Treatments and outcomes
- Record treatments and their associated information.
- Link treatments to medical conditions.
- Record and retrieve treatment outcomes.
- Explore outcome history associated with a treatment.

### AI-assisted analysis
- Submit a natural-language prompt to the backend AI service.
- Receive an AI-generated response through the dashboard.
- Persist analysis task information through the backend.
- Keep AI responses separate from saved measurement records.

### API-first design
- REST endpoints implemented with FastAPI.
- Request validation and structured response schemas.
- Interactive API documentation generated by OpenAPI.
- SQLAlchemy-based database access.

            │             │
            ▼             ▼
┌──────────────────┐  ┌──────────────────┐

## Getting Started

### Prerequisites

Install the following before running the project:

- Python 3.11 or a compatible newer version.
- Node.js and npm.
- Git.
- An API key for the configured external AI service if you want to use AI analysis.

The instructions below use Windows PowerShell. Run the backend and frontend in separate terminals.

### 1. Clone the repository

```powershell
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd <YOUR_REPOSITORY_FOLDER>
```

Replace the placeholders with your GitHub repository URL and folder name.

### 2. Set up the backend

From the repository root:

```powershell
Set-Location .\backend

python -m venv .venv
.\.venv\Scripts\Activate.ps1

python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

If PowerShell blocks virtual-environment activation, you can use the environment's Python executable directly:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 3. Configure environment variables

From the `backend` directory:

```powershell
Copy-Item .env.example .env
```

Open `backend/.env` and configure the values for your local environment.

Example:

```dotenv
APP_NAME=Hackathon Backend
DEBUG=true
DATABASE_URL=sqlite:///./app.db
EXTERNAL_API_KEY=your_api_key_here
```

Replace `your_api_key_here` with your own valid key. Do not commit the populated `.env` file.

The example uses SQLite, so a separate database server is not required for the default local setup.

### 4. Start the backend

From the `backend` directory:

```powershell
python -m uvicorn app.main:app --reload --port 8000
```

The API will be available at:

- Application: http://127.0.0.1:8000/
- Health check: http://127.0.0.1:8000/api/health
- Interactive API documentation: http://127.0.0.1:8000/docs
- OpenAPI schema: http://127.0.0.1:8000/openapi.json

The health endpoint should return:

```json
{
  "status": "online"
}
```

### 5. Start the frontend

Open a second PowerShell terminal at the repository root:

```powershell
Set-Location "C:\Users\jayar\Downloads\blind_hack"

npm --prefix .\frontend install
npm --prefix .\frontend run dev
```

Open the local URL printed by Vite, normally:

http://localhost:5173

The dashboard is configured to use `http://127.0.0.1:8000` as its default API base URL. To use a different backend address, create `frontend/.env.local` and set:

```dotenv
VITE_API_BASE_URL=http://127.0.0.1:8000
```

Restart the Vite development server after changing frontend environment variables.

## API Reference

The backend exposes the following main endpoints.

### General

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/` | Basic application status |
| `GET` | `/api/health` | Health check |
| `POST` | `/api/analyze` | Submit a prompt for AI analysis |

### Medical conditions

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/conditions` | List conditions |
| `POST` | `/api/conditions` | Create a condition |
| `GET` | `/api/conditions/{condition_id}` | Retrieve a condition |
| `PATCH` | `/api/conditions/{condition_id}` | Update a condition |

### Treatments

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/treatments` | List treatments |
| `POST` | `/api/treatments` | Create a treatment |
| `GET` | `/api/treatments/{treatment_id}` | Retrieve a treatment |
| `PATCH` | `/api/treatments/{treatment_id}` | Update a treatment |

### Treatment outcomes

| Method | Endpoint | Purpose |
|---|---|---|
| `POST` | `/api/treatments/{treatment_id}/outcomes` | Create a treatment outcome |
| `GET` | `/api/treatments/{treatment_id}/outcomes` | List outcomes for a treatment |
| `GET` | `/api/outcomes/{outcome_id}` | Retrieve an outcome |

### Health measurements

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/measurements` | List measurements |
| `POST` | `/api/measurements` | Create a measurement |
| `GET` | `/api/measurements/{measurement_id}` | Retrieve a measurement |
| `GET` | `/api/measurements?condition_id=1` | Filter measurements by condition |

For complete request schemas, response examples, and interactive testing, open the Swagger UI at `/docs` while the backend is running.

### Example: create a measurement

Send a `POST` request to `/api/measurements`:

```json
{
  "name": "Heart Rate",
  "value": 72,
  "unit": "bpm",
  "measured_at": "2026-10-13T09:04:00",
  "source": "patient_reported",
  "notes": "Example development record"
}
```

The backend validates the request, stores the record, and returns the created measurement.

### Example: request AI analysis

Send a `POST` request to `/api/analyze`:

```json
{
  "prompt": "Explain what a heart rate measurement of 72 bpm represents in general terms."
}
```

The request is processed by the configured external AI service. A valid API key and a working external service are required for successful analysis.

## Testing

Run backend tests from the `backend` directory with the virtual environment activated:

```powershell
python -m pytest -v
```

You can also verify the backend dependency environment:

```powershell
python -m pip check
```

Check the health endpoint separately:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
```

A useful manual integration check is to create a measurement through the frontend and then retrieve it through `/api/measurements`.

AI-service tests should also cover missing configuration, invalid responses, and external service failures. External API availability can vary independently of the local application.

## Security and Privacy

Health information is sensitive. Keep these practices in mind when developing or deploying the project:

- Never commit API keys, passwords, tokens, or populated environment files.
- Keep `.env`, local databases, virtual environments, caches, and logs out of version control.
- Use synthetic data while developing and demonstrating the application.
- Avoid sending names, contact details, or other personal identifiers in AI prompts.
- Review the external AI provider's data-handling terms before submitting any real health information.
- Configure production secrets through a secure environment or secrets manager.
- Before real-world deployment, add appropriate authentication, authorization, transport security, access controls, and auditing.
- Do not treat AI-generated output as a medical diagnosis or a verified clinical conclusion.

The current project is intended for development and demonstration. A successful local run does not, by itself, establish production readiness or regulatory compliance.
